RevTurbine is monetization for product-led SaaS in one SDK: plans, entitlements, usage limits, trials, and the upgrade prompts that convert — decided per user, inside your app, from a Playbook you keep. We add no latency and our availability never affects your product: the SDK evaluates your Playbook locally, so decisions never depend on our servers.

This page is the whole happy path. It runs in local mode first — no account, no key — and ends with hosted mode, where the same Playbook changes without a deploy.

<Aside type="note" title="Not using React?">
The walkthrough is React because that is the shortest path to something on screen. The engine is framework-agnostic: `import { initRevTurbine } from '@revturbine/sdk/headless'` pulls in no React and runs on Svelte, Vue, plain TypeScript, and Node. Same checks, same decisions; you render the resolved content yourself. See [Headless API](/guides/headless-api/) and [Server-Side Integration](/getting-started/server-side/). Python and Rust SDKs evaluate the same Playbook with byte-identical results.
</Aside>

## Two ideas to hold

Every decision RevTurbine makes combines two things, and the SDK combines them locally:

- The **Playbook** is what you authored, the same for every user: [plans](/concepts/runtime-and-playbook/#plan) and their [variations](/concepts/runtime-and-playbook/#plan-variation), [entitlements](/concepts/runtime-and-playbook/#entitlement) and the [rules](/concepts/runtime-and-playbook/#entitlement-rule) that grant them, [segments](/concepts/runtime-and-playbook/#segment), and [placements](/concepts/runtime-and-playbook/#placement) with their [payloads](/concepts/runtime-and-playbook/#placement-payload). It is one versioned file.
- The **Runtime** is who is asking right now: the [UserContext](/concepts/runtime-and-playbook/#usercontext), their [usage](/concepts/runtime-and-playbook/#usage), and the [entitlement grants](/concepts/runtime-and-playbook/#entitlement-grant) that result. [AccountContext](/concepts/runtime-and-playbook/#accountcontext) is planned, not shipped.

Plain-English definitions, how initialization and context changes drive a decision, and a worked example are on [Runtime and Playbook](/concepts/runtime-and-playbook/). The code for every runtime is on [Initialize the SDK](/getting-started/initialization/).

## 2. Wrap your app

Local mode, no account: the Playbook you just generated is the whole configuration.

```tsx title="src/App.tsx"
import { RevTurbineProvider } from '@revturbine/sdk';
import playbook from './revturbine.playbook.json';
import { useMemo } from 'react';

export default function App() {
  const options = useMemo(() => ({
    localRuntime: { playbook },
    user: { id: 'user_123', plan_handle: 'starter' },
  }), []);

  return (
    <RevTurbineProvider options={options}>
      <YourApp />
    </RevTurbineProvider>
  );
}
```

`plan_handle` is the plan's handle from your Playbook — the value plan-scoped rules match on. In hosted mode it arrives from Stripe on its own (step 7); here you supply it.

## 3. Gate a feature

`<Gate>` renders its children when the user is entitled. When they aren't, it renders the upgrade prompt your Playbook configures for that gate — copy, offer and CTA authored in config, not in your app.

```tsx title="src/components/BatchExport.tsx"
import { Gate } from '@revturbine/sdk';

export function BatchExport() {
  return (
    <Gate id="batch_export_gate" can="batch_export">
      <BatchExportButton />
    </Gate>
  );
}
```

Start the dev server. With the starter Playbook's free plan, the gate shows the upgrade prompt; change `plan_handle` to `'pro'` and the button appears.

## 4. Check and protect in code

For anything that isn't a React subtree — an event handler, a keyboard shortcut, a server route — ask the SDK directly.

```tsx
import { useRevTurbine } from '@revturbine/sdk';

function ExportMenu() {
  const { sdk: rt } = useRevTurbine();

  async function onExport() {
    // Ask: the answer, and nothing else.
    const access = await rt.can('batch_export');

    // Ask and act: runs exportPdf only when entitled; hands back the
    // entitlement so you can open the upgrade prompt otherwise.
    const gated = await rt.gate('export_pdf', () => exportPdf());
    if (!gated.ran) openUpgrade(gated.entitlement);
  }

  return <button onClick={onExport}>Export</button>;
}
```

`can()` returns `{ status, allowed, reason }` — plus `limit` / `used` / `remaining` when a usage or credit rule matched. See [Entitlements](/guides/entitlements/).

## 5. Add a slot

A `<Slot>` is a spot where RevTurbine may show something — a banner, a modal, a toast, a button. Which placement fills it, for which user, with what copy and how often, is decided from the Playbook: targeting, caps, cooldowns and priority between competing prompts are the engine's job, not yours.

```tsx title="src/components/Dashboard.tsx"
import { Slot } from '@revturbine/sdk';

export function Dashboard() {
  return (
    <div>
      <h1>Dashboard</h1>
      {/* An upgrade banner for the users the Playbook targets — or nothing */}
      <Slot id="dashboard_top_banner" surfaceTemplateIds={["banner_placement"]} />
    </div>
  );
}
```

When a user clicks a CTA inside a placement, the SDK calls a resolver you provide — `navigate_to_plans`, `open_checkout_modal`, and so on — so navigation and checkout stay in your code. The starter Playbook uses `navigate_to_plans`; add one line to `options`:

```tsx docs-check=false reason="one option line; the full initRevTurbine options object is shown above"
uiPathResolvers: { navigate_to_plans: () => { window.location.href = '/pricing'; } },
```

Every action type and what it carries: [Placements → UI paths](/guides/placements/).

## 6. Report usage and track events

Usage limits and credits need to know the balance; the Playbook decides what to do about it.

```ts
await rt.update({ usage: { ai_credits_used: 42 } });   // absolute balance, not a delta
await rt.track('ai_generation_completed', { credits: 3 });
```

Balances drive quota meters, low-credit warnings and limit prompts. Events feed targeting and analytics.

## 7. Verify on your server

The browser check drives the UI; your server makes the money-safe decision before paid work runs — with the same SDK, evaluating the same Playbook in-process.

```ts
import { initRevTurbine, RuntimeMode } from '@revturbine/sdk/headless';
import playbook from './revturbine.playbook.json';

export async function POST(request: Request): Promise<Response> {
  const user = await getSignedInUser(request); // your own auth
  const rt = await initRevTurbine({
    runtimeMode: RuntimeMode.LocalOnly,
    localRuntime: { playbook }, // loaded once per process; `revturbine download --live` on deploy
    user: { id: user.id, plan_handle: user.planHandle },
  });
  const result = await rt.can('batch_export');
  if (!result.allowed) return Response.json({ error: 'upgrade_required' }, { status: 402 });
  return runExport(request);
}
```

One instance per request, built from a Playbook you loaded once, so the check
makes no network call. Why the re-check, and which actions need it:
[Client vs Server Enforcement](/concepts/enforcement/). Why a server does not use
hosted mode, and what it can report: [Server-Side Integration](/getting-started/server-side/).

## 8. Go hosted: connect Stripe, change it without a deploy

Everything above works forever in local mode, free. Hosted mode is where you stop deploying to change monetization.

<Steps>

1. **Create an account and connect the CLI.** [revturbine.com/app](https://revturbine.com/app), then `revturbine login` (a browser device flow — no keys to paste).

2. **Connect Stripe** in **Settings → Stripe**. From then on a purchase updates what the user can do with no app code: plan and payment state arrive through a client session. See [Billing & Stripe](/guides/billing/).

3. **Switch the provider to hosted mode.** Mint an ingest key under **Settings → API Token Management → Ingest Keys** and add your app's origins to its allowed origins. Then add the **client-session route** to your server (it mints a short-lived token with your server key, so the plan Stripe holds reaches the SDK) and pass both to the provider:

    ```tsx
    import { RevTurbineProvider } from '@revturbine/sdk';
    import { useMemo, type ReactNode } from 'react';
    import { fetchClientSession } from './revturbine-client-session';

    export function RevTurbine({ userId, children }: { userId: string; children: ReactNode }) {
      const options = useMemo(() => ({
        publicKey: process.env.NEXT_PUBLIC_REVTURBINE_PUBLIC_KEY!, // public key, safe in the browser
        user: { id: userId },                                      // plan_handle now comes from Stripe
        clientSession: fetchClientSession,                         // calls YOUR route; see Client sessions
      }), [userId]);

      return <RevTurbineProvider options={options}>{children}</RevTurbineProvider>;
    }
    ```

    The route and the `fetchClientSession` function are on [Client sessions](/guides/client-sessions/); every initialization variant is on [Initialize the SDK](/getting-started/initialization/).

4. **Change something and reload.** Open the dashboard, edit the banner's copy or the free plan's export limit, launch the release. The SDK picks it up on its next refresh — no deploy. Or do it from the terminal: `revturbine download --live`, edit, `revturbine validate`, `revturbine diff --live`, `revturbine launch`.

</Steps>

That loop — see what converted, change the Playbook, launch — is the product. Your agent can drive it too: [Add RevTurbine with a Coding Agent](/guides/coding-agent/).

## Why RevTurbine

<CardGrid>
  <Card title="Decisions, not just rendering">
    Caps, cooldowns, eligibility, and priority across competing placements are decided for you. One `<Slot>` returns the winner. No client-side orchestration, no homegrown segment logic.
  </Card>
  <Card title="Entitlements and prompts in one engine, tied to billing">
    A `<Slot>` surfaces usage warnings, trial nudges and lifecycle prompts tied to billing state; `rt.can()` confirms or denies access. Gate a feature and show the upgrade prompt that converts it, from one Playbook.
  </Card>
  <Card title="Changed by product, not by a deploy">
    Drop a slot once. Copy, targeting, limits, offers and prices change in the dashboard or through the CLI; resolvers keep navigation in your code. Every launch is a versioned release you can roll back.
  </Card>
  <Card title="The same answer everywhere">
    `@revturbine/sdk/headless` imports no React; Python and Rust evaluate the same Playbook. A cross-language gate diffs their decisions byte-for-byte, so a check answers identically wherever you make it.
  </Card>
</CardGrid>
