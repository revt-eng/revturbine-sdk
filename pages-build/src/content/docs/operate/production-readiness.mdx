RevTurbine is safe to run in production from day one: we add no latency and our availability never affects your product. Decisions never have critical dependence on our servers. The RevTurbine SDK runs inside your app, and on your backend where you verify. It evaluates entitlements and placements locally, as a pure function of your Playbook and the current user context.

We push additional inputs to your local engine: aggregated frequency caps, prioritization scores as available. These are additive; nothing breaks or blocks if not present. This page is the checklist for the rest.

## Client vs server

The one decision that matters most: **the client check drives the UI; your server makes the money-safe decision.** Read [Client vs Server Enforcement](/concepts/enforcement/) before shipping anything billing-critical.

## Keys

Every credential RevTurbine issues, where it is minted, and where it may live. There is no live/test split on keys; use `environmentId` (below) and `test: true` to separate traffic.

| Credential | Looks like | Minted | Lives in | Authorizes |
|---|---|---|---|---|
| **Publishable ingest key** | `rtk_…` (type `public`) | RevTurbine dashboard → **Settings → API tokens → Ingest keys**. An origin allowlist is required. | Your browser bundle — safe to ship | Playbook delivery, event ingest, client-safe theme reads. Tenant-bound; cannot call management APIs. |
| **Server token** | `rtk_…` (type `server`) | **Settings → API tokens → Server token** (one per user; rotate from the same place) | Your backend only | Playbook delivery from a server, management APIs. Rejected on a browser-like request. |
| **Client-session mint secret** | `rt_secret_…` | Issued per tenant, application and environment | Your backend only | `POST /api/sdk/client-sessions` — mints the client-session tokens below. Bound to an origin allowlist. |
| **Client-session token** | `rt_client_…` | Your backend, via the mint secret; short-lived (~10 minutes) | The browser, in memory only — the SDK requests it through your `clientSession` callback | `GET /api/sdk/client-context`: the server-derived plan, trial and payment state for one user. |
| **CLI credential** | `rtk_…` (type `client`) | `revturbine login` (browser device flow), one per machine | The developer's machine | The CLI. |
| **MCP token** | `rtk_…` (type `mcp`) | **Settings → API tokens → MCP** | Your agent tooling | The RevTurbine MCP server. |

Which one goes where:

- **In the browser**, pass the publishable ingest key as `apiKey`. (`ingestPublicKey` is accepted as well; when both are set it takes precedence for delivery and ingest.) Never a server token: RevTurbine refuses a server token presented from a browser.
- **On your backend**, pass the server token as `apiKey` — the sample on [Server-Side Integration](/getting-started/server-side/) reads it from `REVTURBINE_API_KEY`.
- **For server-derived context**, keep the mint secret on your backend and hand the SDK a `clientSession` callback; the SDK re-mints on expiry. See [Configuration → Server-derived context](/reference/configuration/#server-derived-context-clientsession).
- **Local mode needs no key at all.**

Stamp `environmentId` (`'production'` / `'staging'`) so analytics stays separated by deployment, and `test: true` on instances that generate test traffic.

## Versioning

Pin `@revturbine/sdk` and the CLI per project; `revturbine --help` from the project-pinned CLI is authoritative for its command surface. A change to any `@public` signature requires a CHANGELOG entry — CI enforces it — and the Playbook schema version the SDK expects is listed on the [Compatibility Matrix](/reference/compatibility/). Pin the SDK to a version whose schema matches the Playbook you deploy.

## Fail-closed checks

Entitlement checks fail closed: a check that can't produce an affirmative grant denies rather than leaking a paid feature. The Playbook is cached locally, so real answers need no round trip, and billing-critical actions are re-checked on your server before value is granted. Tune what a slot renders on provider failure with `providerFailureSlotBehavior` (default: render nothing). See [Error Handling](/guides/error-handling/).

## Local-only limits

In `local_only` mode the SDK evaluates entirely from the bundled Playbook — no network. That's great for tests and no-backend demos, but be aware:

- Usage is **client-reported and client-only** — not authoritative. Don't meter billing off it.
- There are **no real-time config updates** — you ship a Playbook snapshot.
- Events go to `localStorage`, not the ingest pipeline.

See [Runtime Modes](/guides/runtime-modes/) to choose between local mode (`local_only`), hosted mode (`revturbine_server`), and `custom_endpoints`.

## Caching

The SDK caches placement decisions and interaction state per user and persists them, so repeat checks are instant and dismiss/snooze survive reloads. The cache clears on identity change (`identify` / `reset`) and when the config updates. If you see a stale decision after a config change, confirm the user context was re-identified.

## Config versioning

Every placement decision carries the `config_version` it was evaluated against, so you can trace a decision back to the exact Playbook that produced it. A Playbook moves from **draft → Release**, so each launched change is reviewed, versioned, and traceable.

## Test plan changes before you deploy

Because monetization changes ship as config, you can verify them without touching app code:

- **CLI:** validate and diff `./revturbine.playbook.json`, or upload it as a draft and run `preview` plus `evaluate --draft --user <file>` before launch. The [CLI reference](/reference/cli/) lists the required selectors.
- **`local_only`:** load a candidate `revturbine.playbook.json` in a test build and exercise the gates and placements against fixture users.
- **[Debugging Decisions](/operate/debugging/):** use `explainPlacementDecision()` to see exactly why a decision resolved the way it did.
