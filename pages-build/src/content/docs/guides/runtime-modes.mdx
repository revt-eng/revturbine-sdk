Two modes matter for most apps: **local** and **hosted**. A third, `custom_endpoints`, routes hosted mode's calls through your own proxy.

## Hosted mode

**Hosted mode is how you change monetization without a deploy.** RevTurbine stores and versions your Playbook; the SDK in your app keeps a fresh local copy and decides from it.

What it gives you:

- **Change without deploying.** Edit plans, entitlements, targeting and prompts in the RevTurbine dashboard, with your coding agent, or through the CLI. Draft, review, launch. The SDK picks up the new release on its next refresh.
- **Versioned Playbooks.** Every launch is an immutable Release with history. Roll back by restoring any earlier one.
- **Analytics.** Conversion and usage analytics, so you can see what's working. Growth adds deeper analytics and self-driving growth recommendations.
- **Signals your app doesn't hold.** Billing status from Stripe, trial state, per-customer exceptions and end-user behavior follow the user. Caps and cooldowns hold across devices, and an exception applies wherever that user shows up.

What doesn't change: the RevTurbine SDK runs inside your app, and on your backend where you verify. It evaluates entitlements and placements locally, as a pure function of your Playbook and the current user context. Hosted mode changes where the Playbook and user state come from, not where decisions run. We add no latency, and our availability never affects your product.

In code: `runtimeMode: RuntimeMode.Server` (`revturbine_server`).

## Local mode

**Local mode ships the Playbook with your app.** You version it in your own repo, and changing it is a deploy. No account, always free, and production-capable on its own. Every decision is made the same way as in hosted mode.

In code: `runtimeMode: RuntimeMode.LocalOnly` (`local_only`) with `localRuntime: { playbook }`.

## Which one

1. Getting started, building a demo, or shipping a Playbook that rarely changes? **Local.**
2. Want to change monetization without deploying, see analytics, or set per-customer exceptions? **Hosted.**
3. Need RevTurbine's calls to go through your own proxy? **Hosted, with `custom_endpoints`.**

## Mode comparison

| Mode | Where the Playbook comes from | What RevTurbine provides | Required config |
|---|---|---|---|
| **Local** (`local_only`) | Bundled with your app | Nothing at runtime; optional anonymous adoption beacon | `localRuntime: { playbook }` |
| **Hosted** (`revturbine_server`) | RevTurbine, cached locally and refreshed in the background | Playbook delivery and versioning; user state (billing, trials, exceptions, behavior); analytics | `tenantId`, `apiKey`, `endpoint` |
| **Hosted via your proxy** (`custom_endpoints`) | RevTurbine, through endpoints you own | Same as hosted | Base config + `endpointOverrides` |

Set the mode with the typed **`RuntimeMode`** constant rather than a raw string:

```ts
import { RuntimeMode } from '@revturbine/sdk';
// runtimeMode: RuntimeMode.LocalOnly | RuntimeMode.Server | RuntimeMode.CustomEndpoints
```

`local_only` makes no config or decisioning calls and does not send clickstream
events to RevTurbine ingest. A keyless, anonymous `sdk_init` adoption beacon is
the one network exception. Set `anonymousTelemetry: false` (or
`previewMode: true` for docs and examples) when the process must make zero
RevTurbine requests.

## Copy-Paste Setup

<Tabs>
<TabItem label="Local-only (start here)">

```ts
import { initRevTurbine, createLocalRuntimeConfig } from '@revturbine/sdk';
import playbook from './revturbine.playbook.json';

const sdk = initRevTurbine(
  createLocalRuntimeConfig({
    tenantId: 'my-app',
    apiKey: 'local',
    endpoint: 'http://localhost',
    mode: 'react',
    localRuntime: {
      playbook,
      storageKey: 'my-app:revturbine-local-runtime',
    },
  }),
);
```

<Aside type="tip">
In `local_only` mode the SDK evaluates all targeting rules, entitlements, and placement decisions client-side using the loaded Playbook. Clickstream events are not sent to RevTurbine ingest; local consumers and runtime persistence still work. The one network exception is the anonymous adoption beacon described above.
</Aside>

## Migrating from local to hosted mode

When you're ready for production, the change is a single config swap. Your component code stays the same:

```diff
  <RevTurbineProvider
    options={{
-     tenantId: 'my-app',
-     apiKey: 'local',
-     endpoint: 'http://localhost',
-     runtimeMode: RuntimeMode.LocalOnly,
-     localRuntime: { playbook },
+     tenantId: process.env.REVTURBINE_TENANT_ID!,
+     apiKey: process.env.REVTURBINE_API_KEY!,
+     endpoint: 'https://revturbine.com/app',
+     runtimeMode: RuntimeMode.Server,
    }}
    defaultUserId="user_123"
  >
```

## Provider Fallback Strategy

Provider fallbacks are orthogonal to runtime mode. You can configure them in any mode when you want explicit provider-chain control.

**Available options:**

- `provider`: primary provider.
- `providerFallbacks`: ordered fallback provider list.
- `providerFailureSlotBehavior`: `'invisible'` (default) or `'placeholder'`.

**Behavior:**

1. SDK calls primary provider first.
2. If primary fails, SDK logs a warning and executes fallbacks in order.
3. If all configured providers fail for a method, SDK disables itself.
4. Disabled SDK returns hidden or placeholder placement output based on `providerFailureSlotBehavior`.

### Recommendation by Mode

1. **`revturbine_server`:** add at least one fallback provider for resilience.
2. **`custom_endpoints`:** strongly recommend fallbacks because proxy integrations can be brittle during deploys.
3. **`local_only`:** provider fallbacks are optional; local runtime resolvers are often sufficient.

### Hosted mode with fallback

```ts
import { initRevTurbine, createServerRuntimeConfig } from '@revturbine/sdk';

const sdk = initRevTurbine({
  ...createServerRuntimeConfig({
    tenantId: 'tenant_abc',
    apiKey: 'rt_live_xxx',
    endpoint: 'https://revturbine.com/app',
    mode: 'react',
  }),
  provider: primaryProvider,
  providerFallbacks: [fallbackProviderA, fallbackProviderB],
  providerFailureSlotBehavior: 'placeholder',
});
```

## Production Checklist

1. Start with `local_only` to validate your integration and placement slots.
2. When ready, switch to `RuntimeMode.Server` and provide real credentials.
3. Configure a primary RT provider first in the chain.
4. Add at least one fallback provider in `providerFallbacks`.
5. Keep fallback providers ordered by trust and operational readiness.
6. Choose `providerFailureSlotBehavior` intentionally per surface criticality.
7. Monitor console warnings for provider-chain failures.
8. Assume fail-closed behavior: if all providers fail, SDK disables itself and slots render placeholder or invisible output.
